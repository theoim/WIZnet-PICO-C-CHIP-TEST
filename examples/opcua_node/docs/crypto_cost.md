# RSA / ECC 암호 연산 비용 — 실측

**측정일:** 2026-10-15 (RSA 4회, ECC 4회, 전부 실기)
**도구:** `examples/crypto_bench`, `tools/bench_matrix.sh`
**저장소 상태:** `273e868` + 미커밋 변경

---

## 1. 결론

**부품은 RP2350으로 간다. 그리고 정책은 ECC가 RSA보다 압도적으로 싸다.**

| | RSA-2048 (Basic256Sha256) | ECC P-256 |
|---|---|---|
| RP2040 @200MHz | 5,050 ms — **불가** | **384 ms** |
| RP2350 @150MHz | 1,229 ms — 가능 | **264 ms** |

기준은 open62541 클라이언트의 기본 타임아웃 5,000 ms다.

세 가지가 확정됐다.

1. **RP2040에서 RSA-2048은 어떤 설정으로도 안 된다.** 이미 정격(133 MHz)을
   넘긴 200 MHz에서 측정했고 그래도 타임아웃을 넘는다.
2. **ECC 정책을 쓰면 두 부품 모두 보안이 성립한다.** RP2040조차 384 ms다.
3. **ECC 경로에서는 동시 접속 문제가 사라진다.** 4개 동시 핸드셰이크가
   RP2040 1,536 ms, RP2350 1,056 ms다. **RSA 경로에서는 남는다**(6-2).

### ⚠ 그러나 성능이 제품을 결정하지 않는다 (2026-10-15 상호운용성 조사)

외부 조사 결과 **ECC 단독 출하는 범용 산업 시장에서 성립하지 않는다.**
Siemens SIMATIC/WinCC, Beckhoff TwinCAT, Ignition, KEPServerEX, Prosys,
Python asyncua의 공개 정책 목록에 ECC가 없고, UAExpert와 node-opcua는 미확인이다.
공통분모는 Basic256Sha256이다. 상세는 6-5.

**그래서 제품 구조는 둘 중 하나를 고르는 것이 아니다.**

```
RP2350 + W6300    Basic256Sha256 = 호환성 경로 (유지 필수)
                  ECC            = 성능 경로 (상대가 지원하면)
                  → 범용 Secure OPC UA SKU

RP2040 + W5500    ECC-only 범용 SKU = NO-GO (호환성 + 난수원 두 가지 이유)
                  클라이언트 고정 특화 구성 = 조건부
```

RP2350의 RSA 1,229 ms는 **버리는 숫자가 아니라 호환성 경로의 비용**이다.

**"RP2040은 보안이 불가능하다"는 2026-10-15 오전의 결론은 틀렸다.** RSA만
측정하고 내린 결론이었다. 정확한 서술은 **"RP2040에서 RSA-2048 정책은 불가,
ECC 정책은 가능"**이다.

단, RP2040 보안 등급에는 **난수 전제**가 붙는다 (6-4 참조).

## 2. 측정 환경

4개 이미지를 한 스크립트로 빌드해 교차 오염을 막았다. 이 저장소에는
`crypto_bench.uf2`를 만드는 빌드 디렉토리가 여러 개 있어서, **어느 이미지였는지가
기록되지 않으면 수치가 무의미해진다.** 그래서 이미지가 부팅 시 스스로 보고한다.

```
================ crypto_bench ================
  board    W6300_EVB_PICO2
  part     RP2350 (Cortex-M33)
  clk_sys  150000000 Hz
  bignum   assembly (MBEDTLS_HAVE_ASM)
  ecp      NIST_OPTIM on
  git      273e868
  built    2026-10-15T02:16:02Z
==============================================
```

벤치는 네트워크를 쓰지 않는다(`pico_stdlib` + `mbedcrypto` + `mbedx509`만 링크).
**이더넷 칩은 이 수치에 무관하다** — 보드 이름은 MCU와 핀 정의만 고른다.

### 배너가 실제로 사고를 잡았다

ECC 재측정 때 **빌드 완료 3초 전에 플래시가 끝나** 옛 이미지가 올라갔다.
배너에 `ecp` 줄이 없고 `built` 시각이 이전 빌드였기 때문에 즉시 발견했다.
그 줄이 없었으면 "NIST_OPTIM을 켜도 변화 없음"이라는 **거짓 결론**을 기록했을 것이다.

### 클럭이 공정하지 않다 — RP2040 쪽이 유리하게 측정됐다

`CMakeLists.txt:147`이 `PICO_USE_FASTEST_SUPPORTED_CLOCK=1`을 전역으로 건다.

```
RP2040   platform_defs.h:86    → 200 MHz   (데이터시트 정격 133 MHz, 즉 오버클럭)
RP2350   platform_defs.h:115   → 150 MHz   (정격 최대, 스톡)
```

RP2040은 정격을 1.5배 넘긴 상태이고 RP2350은 스톡이다. 그래도 RSA에서 4.1배
차이가 난다.

## 3. 실측값

### 3-1. OPC UA 보안 핸드셰이크 — RSA-2048 (ms)

| | bignum C | bignum 어셈블리 |
|---|---|---|
| RP2040 @200MHz | 6,973 | 5,050 |
| RP2350 @150MHz | 2,017 | **1,229** |

사이클 수로 환산하면 부품 효과는 5.48배다 (1,010M → 184M 사이클).
Cortex-M33에 32×32 곱셈 명령이 있고 M0+에는 없다는 차이가 그대로 나온다.

### 3-2. 같은 핸드셰이크 — ECC P-256 (ms)

| | NIST_OPTIM 꺼짐 | 켜짐 (flash) | 켜짐 (RAM 실행) |
|---|---|---|---|
| RP2040 @200MHz | 2,458 | 384 ~ 471 | **371.8** |
| RP2350 @150MHz | 1,697 | 264 ~ 285 | **258.5** |

**flash 열이 범위인 것은 오차가 아니라 실제 현상이다.** 코드 배치에 따라 같은
암호 코드가 최대 35% 흔들린다 (4-2 참조). **RAM 열이 기준값이다.**

합계 구성(어셈블리 + NIST_OPTIM):

| 연산 | RP2040 | RP2350 |
|---|---|---|
| 임시 키쌍 생성 (ECDH keygen) | 43.69 | 30.86 |
| 키 합의 (ECDH agree) | 118.18 | 78.61 |
| 서명 1회 (ECDSA sign) | 49.26 | 35.74 |
| 상대 검증 1회 (ECDSA verify) | 169.96 | 116.87 |
| 키유도 | 2.98 | 1.94 |
| **합계** | **384.07** | **264.02** |

부품 효과는 1.45배(시간), 사이클로는 1.94배다. **RSA의 5.48배와 비교하면
훨씬 작다** — ECC의 병목은 곱셈보다 모듈러 감산과 점 연산에 있고, M33의
곱셈기와 어셈블리 경로가 그만큼 덜 먹는다. 측정값에서 읽은 것이고 원인은 추정이다.

### 3-3. 개인키 연산 — RSA (ms)

| 연산 | RP2040 asm | RP2040 C | RP2350 asm | RP2350 C |
|---|---|---|---|---|
| RSA-2048 sign | 1,647 | 2,274 | **402** | 659 |
| RSA-2048 OAEP decrypt | 1,544 | 2,128 | **381** | 621 |
| 첫 sign (blinding 캐시 없음) | 1,895 | 2,566 | 551 | 825 |

### 3-4. 공개키 연산 — RSA (ms)

| 연산 | RP2040 asm | RP2040 C | RP2350 asm | RP2350 C |
|---|---|---|---|---|
| RSA-2048 verify | 103.5 | 146.5 | **21.1** | 38.1 |
| RSA-2048 OAEP encrypt | 104.0 | 147.0 | **21.4** | 38.3 |

### 3-5. 메시지마다 드는 비용 — SignAndEncrypt, 8 KB

Basic256Sha256은 메시지를 암호화하면서 **서명도 한다.** 둘 다 들어간다.

| | RP2040 | RP2350 |
|---|---|---|
| AES-256-CBC 8 KB | 6.32 ms | 4.00 ms |
| HMAC-SHA256 8 KB | 5.08 ms | 2.75 ms |
| **합계** | **11.40 ms → 5.75 Mbit/s** | **6.75 ms → 9.71 Mbit/s** |
| (AES만 보면) | 10.37 Mbit/s | 16.38 Mbit/s |

**AES 행만 인용하면 약 2배 과장이 된다.** 괄호의 수치를 보안 처리량으로
쓰면 안 된다. 벤치 출력 자체에 그 경고를 넣어 뒀다.

참고 — SHA-256 8 KB는 RP2040 4.96 ms / RP2350 2.65 ms다. HMAC의 고정
오버헤드는 0.12 ms뿐이다.

### 3-6. 파싱

| 연산 | RP2040 | RP2350 |
|---|---|---|
| 개인키 DER 파싱 | 약 215 us | 약 190 us |
| 인증서 파싱 | 약 160 us | 약 157 us |

시작 시 1회 / 클라이언트당 1회라 무게가 없다.

## 4. 설정 하나가 ECC를 6.4배 바꿨다 — 가장 중요한 발견

```
MBEDTLS_ECP_NIST_OPTIM     P-256 전용 빠른 모듈러 감산
```

이 옵션이 우리 설정에 **없었다.** 켜고 재측정한 결과:

```
RP2040   2,458 → 384 ms    6.40배
RP2350   1,697 → 264 ms    6.43배
RSA      변화 없음          (소수점까지 동일 — 옵션이 ECC만 건드렸다는 확인)
```

비용은 **코드 증가, RAM 증가 없음.** `.text`가 RP2040 122,276 → 129,676,
RP2350 114,128 → 121,368이다. 단 이 증가분에는 **ECC 벤치 코드와 최적화가
같이 들어 있어** 둘을 분리한 값은 측정하지 않았다.

### 왜 빠져 있었나 — 재발 방지가 필요한 구조

우리 빌드는 `MBEDTLS_CONFIG_FILE`로 `port/mbedtls/inc/ssl_config.h`를 쓴다.
**이 파일은 상위 `mbedtls_config.h`를 보강하는 것이 아니라 완전히 교체한다.**
따라서 mbedTLS 기본값으로 켜져 있던 옵션(`mbedtls_config.h:784`)이 조용히 꺼졌다.

**같은 이유로 꺼져 있는 다른 옵션이 더 있을 수 있다. 미확인이다.**
성능이 예상보다 나쁘면 알고리즘을 의심하기 전에 이 파일을 먼저 볼 것.

### 이 발견 전에 두 번 틀린 판단을 했다

1. "ECC는 수십 ms일 것" — 실측 2,458 ms. 5배 이상 틀렸다
2. "RP2350에서 ECC가 RSA보다 비싸니 ECC 경로를 닫자" — 실측 264 ms로 4.7배 싸다

둘 다 **설정이 틀린 상태의 측정값으로 알고리즘을 판단**한 결과다.

## 4-2. ECC 수치는 코드 배치에 흔들린다 — RSA는 안 흔들린다

엔트로피 모듈을 추가했을 뿐인데(암호 코드는 한 줄도 안 건드렸다) ECC가 전부
느려졌다.

| | 변경 전 | 변경 후 | 차이 |
|---|---|---|---|
| RP2040 ECC 합계 | 384.07 | 471.13 | **+22.7%** (keygen은 +34.6%) |
| RP2350 ECC 합계 | 264.02 | 285.40 | +8.1% |
| RSA sign (대조) | 1,647.36 | 1,648.29 | **+0.06%** |

**RSA는 여섯 빌드 전부에서 0.1% 안에 들어온다.** ECC만 흔들린다.

### RAM 실행으로 원인을 확인했다

`pico_set_binary_type(copy_to_ram)`으로 이미지 전체를 RAM에 올려 XIP 캐시를
없앴다. 결과가 부품마다 다르다.

| | RP2040 | RP2350 |
|---|---|---|
| ECC 합계 | 471.13 → **371.82** (−21.1%) | 285.40 → **258.50** (−9.4%) |
| RSA sign | 1,648.29 → 1,646.55 (−0.1%) | 402.03 → **431.65 (+7.4%)** |
| 개인키 파싱 | 231.2 → 136.2 us (−41%) | 214.4 → 104.0 us (−51%) |
| 인증서 파싱 | 152.4 → 73.3 us (−52%) | 175.9 → 64.1 us (−64%) |
| AES 8 KB | 6.32 → 6.32 (같음) | 4.00 → 4.16 (+4%) |

**산포가 사라진다.** flash에서 `ECDSA verify`는 avg 126.63 / min 123.95(2.2%)였는데
RAM에서는 115.37 / 115.31(0.05%)이다. `HMAC 32 B`는 flash 128.1/120.0(6.3%)에서
RAM 100.0/100.0(0%)이 된다.

**확정된 것:** ECC와 X.509 파싱은 **플래시 접근에 묶여 있었다.** 분기 많고 코드가
흩어진 작업일수록 캐시 미스가 지배한다. 파싱이 41~64% 빨라진 것이 가장 분명한 증거다.

**추정:** RP2350에서 RSA가 느려진 이유는 `copy_to_ram`일 때 코드와 데이터가 같은
SRAM을 다투는 것이고, 플래시 실행에서는 코드가 XIP 캐시 / 데이터가 SRAM으로
경로가 분리된다는 것이다. M0+는 메모리 대역을 덜 먹어 경합이 드러나지 않는다.
**확인하지 않았다.**

### 쓸 수 있는 결론

1. **암호 방식을 비교할 때는 RAM 빌드가 기준기다.** 배치 잡음이 없다.
   플래시 빌드는 현실 수치용이고, 두 숫자를 같이 적는다.
2. **제품에 전체 RAM 실행은 쓸 수 없다.** OPC UA 서버 바이너리는 벤치보다 크다.
   쓸 수 있는 형태는 **ECP 핫 함수만 RAM에 올리는 것**(`__not_in_flash_func`)이고,
   그러면 ECC 이득만 받고 RP2350의 RSA 손실은 피할 가능성이 있다. **미검증.**
3. **ECC 우위는 어느 조건에서도 유지된다** — RP2040 13.6배, RP2350 5.1배.

재현: `tools/bench_matrix.sh`의 `rp2040_ram` / `rp2350_ram` 변형. 배너의 `code` 줄이
`RAM (copy_to_ram, no XIP cache)`인지 확인한다.

## 4-3. L2 빌드 — Flash +103 KB, 정적 RAM +8.8 KB (2026-10-15 실측)

`opcua_node`를 암호화 off/on 두 번 빌드해 비교했다. 보드 `W6300_EVB_PICO2`,
같은 툴체인·같은 커밋.

| 섹션 | OFF | ON | 증가 |
|---|---|---|---|
| `.text` | 239,616 | 326,816 | +87,200 (+36.4%) |
| `.rodata` | 58,764 | 74,924 | +16,160 (+27.5%) |
| `.data` | 54,344 | 54,352 | +8 |
| `.bss` | 10,300 | 19,056 | +8,756 |
| **Flash (text+rodata+data)** | 352,724 | **456,092** | **+103,368 (+29.3%)** |
| **정적 RAM (data+bss)** | 64,644 | **73,408** | **+8,764** |

보드 플래시는 4 MB다(`pico2.h:78`). **456 KB는 11%이고 Flash는 제약이 아니다.**

**이 문서의 이전 예상이 틀렸다** — "mbedTLS RSA+AES+SHA+X.509를 넣으니 힙보다
Flash가 먼저 터질 가능성이 높다"고 적었는데, 4 MB 중 103 KB다.

### 이 숫자에 없는 것

**정적 메모리만이다.** 실제 제약일 수 있는 둘이 빠져 있다.

```
SecureChannel 버퍼    채널·세션마다 붙는다. 소켓 4개면 4배
mbedTLS 힙 피크       핸드셰이크 중 임시 할당. 실기 실행이 필요하다
```

`.bss` +8.8 KB는 정책 객체와 고정 버퍼이고 핸드셰이크 중 힙은 포함하지 않는다.

### 두 정책을 모두 넣은 비용이다

amalgamation은 RSA·ECC 정책 소스를 전부 포함하고 정의로 켠다(6-6 참조).
즉 위 수치가 **"Basic256Sha256 호환 경로 + ECC 성능 경로"를 함께 싣는 비용**이고,
현재 구조에서는 한쪽만 빼서 줄이는 선택지가 없다.

### 빌드 방법 (함정 두 개)

```bash
cmake -S . -B build_l2_on -G "MinGW Makefiles" \
  -DCMAKE_MAKE_PROGRAM="<mingw32-make>" \
  -Dpioasm_DIR="<기존빌드>/pioasm-install/pioasm" \
  -DBOARD_NAME=W6300_EVB_PICO2 -DPICO_SDK_PATH=./libraries/pico-sdk \
  -DOPCUA_ENABLE_ENCRYPTION=ON
```

**1. 제너레이터는 MinGW여야 한다.** W6300 QSPI 드라이버가 PIO를 쓰고, SDK가
`pioasm`을 **호스트용으로** 빌드한다. NMake 경로에는 호스트 C++ 툴체인이 없다.

**2. `pioasm`은 기존 빌드 것을 재사용한다.** SDK가 `pioasm_DIR`을
`find_package(pioasm CONFIG)`로 집어간다(`pico-sdk/tools/CMakeLists.txt:112-116`).
이 머신에서는 호스트 C++ 빌드가 깨져 있어 새로 만들 수 없다.

## 5. 이 숫자가 아닌 것

**바닥값이다.** 산술만 재고 왕복·인코딩·PKI 목록 순회·DRBG 시딩·할당·이더넷
전송이 빠져 있다. 실제 클라이언트가 보는 시간은 더 길다.

**인증서 체인 검증값은 유효하지 않다.** `crypto_bench.c`가 같은 인증서를
leaf와 trust anchor로 둘 다 넣어서 mbedTLS가 즉시 통과시킨다(25~44 us).
진짜 검증은 공개키 연산 1회라 RSA에서 RP2350 약 21 ms다. **미수정.**

**RP2350에서 설명되지 않은 값.** HMAC 32 B와 키유도가 어셈블리 설정에 따라
움직였다(106.2 → 135.0 us). SHA 8 KB와 AES 8 KB는 소수점까지 같고 RP2040에서는
HMAC도 같았다. 코드 배치 변화로 XIP 캐시(8 KB) 적중률이 달라진 것이 후보지만
**확인하지 않았다.** 설계 판정에는 영향이 없다.

## 6. 설계 판정

### 6-1. 워치독은 존재하지 않는다

`crypto_bench`와 `current_state.md:170`이 "RSA 연산 중 워치독이 kick되지
않는다"고 서술하지만, **`examples/opcua_node`에는 워치독이 없다.**
`watchdog_enable()` 호출이 없고 `opcua_settings.h:149`의 `reboot_reason`에
`1=watchdog` 값만 정의돼 있다.

현재 결함이 아니다. 넣을 때 타임아웃을 핸드셰이크 시간보다 충분히 길게 잡는다.

### 6-2. 동시 핸드셰이크 — ECC를 쓰면 해소된다

이벤트루프가 한 번의 iterate에서 소켓 4개를 순서대로 돈다
(`open62541_wiznet_eventloop.c:827,833`). 단일코어 협력 루프라 OPN 처리는 직렬이다.

```
RSA   RP2350   4 × 1,229 = 4,916 ms    ← 타임아웃 경계
ECC   RP2350   4 ×   264 = 1,056 ms    ← 여유 큼
ECC   RP2040   4 ×   384 = 1,536 ms    ← 여유 큼
```

**이 항목은 2026-10-15에 다시 열렸다.** 처음에는 "ECC를 쓰는 한 소켓 수를 2개로
줄이는 안은 폐기 가능"이라고 적었고 조건도 함께 적었다. 상호운용성 조사로
**Basic256Sha256 병행이 확정되면서 그 조건이 항상 성립한다.**

ECC를 제시해도 클라이언트가 RSA를 고르면 RSA 경로를 탄다. 설비 전원 복구로
4대가 동시에 재접속하는 상황에서 그 4대가 Siemens·Beckhoff 같은 RSA 전용이면
마지막 클라이언트가 4,916 ms다. **소켓 수 결정은 미결 항목으로 되돌린다.**

### 6-3. RSA 연산은 쪼갤 수 없고 ECC는 쪼갤 수 있다

벤더링된 mbedTLS 3.6.0에 `MBEDTLS_ECP_RESTARTABLE`은 있으나
(`mbedtls_config.h:839`) **RSA에 대응되는 기능이 없다**(`rsa_restart` 심볼 부재).

즉 ECC 정책에서는 핸드셰이크를 여러 루프 이터레이션에 나눠 양보시킬 수 있다.
264 ms라면 굳이 필요 없을 수도 있다 — 필요해지면 그때 켠다. 현재 꺼져 있다.

### 6-4. 엔트로피 — RP2040 보안 등급의 전제

**RP2350에 하드웨어 TRNG가 있다. SDK 코드로 확인됐다.**

```
rp2350/hardware_regs/include/hardware/platform_defs.h:74    HAS_RP2350_TRNG 1
rp2_common/pico_rand/include/pico/rand.h:76,102              기본 엔트로피원으로 TRNG 사용
rp2350/hardware_structs/include/hardware/structs/trng.h      존재
```

**RP2040에는 없다.** 그리고 **ECDSA는 서명마다 난수를 쓴다** — 그 난수가
예측 가능하거나 재사용되면 개인키가 노출된다. 성능이 아니라 보안 문제다.

```
RP2350   ECC 264 ms · RSA 1,229 ms · TRNG 있음     → 보안 등급 성립
RP2040   ECC 384 ms · RSA 불가     · TRNG 없음     → 난수 해결이 전제
```

**RP2040 보안 등급은 성능으로 열렸고 난수로 막혀 있다.** ROSC 기반 난수의
품질 근거를 문서화하거나 외부 난수 칩이 필요하다.

### 연결됐다 (2026-10-15) — 그리고 이미 있던 구현을 뒤늦게 찾았다

**`port/mbedtls/src/wiz_entropy.c`로 공용화했고 실기에서 작동을 확인했다.**

처음에 "저장소에 엔트로피 소스가 없다"고 적었는데 **부정확했다.**
`mbedtls_hardware_poll`과 `MBEDTLS_ENTROPY_HARDWARE_ALT`가 없다는 건 맞지만,
`port/wiz-claw/src/wiz_claw_tls.c:42`에 `get_rand_32()` 기반 콜백이
`mbedtls_entropy_add_source()`로 등록돼 이미 하드웨어에서 돌고 있었다.
file-static이라 OPC UA 쪽에서 보이지 않았을 뿐이다. 새로 쓰지 않고 뽑아냈다.

실측:

| | RP2350 (TRNG) | RP2040 (ROSC) |
|---|---|---|
| CTR-DRBG seed | 0.97 ms (RAM 0.68) | 1.57 ms (RAM 1.33) |
| entropy 1 KB | 0.68 ms | 2.56 ms (≈3.2 Mbps) |

**시드 비용이 핸드셰이크의 0.3%다.** 기존 합계에서 빠져 있던 "DRBG seeding" 항목이
정량화됐고 예산에 영향이 없다.

`wiz_entropy.h`는 **하드웨어 RNG가 없는 부품에서 빌드를 멈춘다.**
`WIZ_ENTROPY_ALLOW_NO_TRNG`를 쓰는 쪽이 자기 빌드에 정의해야 넘어간다 —
링 오실레이터 소스를 `SOURCE_STRONG`으로 등록하는 결정을 누군가 의식적으로
내리게 만드는 장치다. crypto_bench는 측정이 목적이라 켜 뒀다.

**아직 판정 못 한 것:** RP2040 ROSC 출력의 품질. raw 덤프 32바이트를 찍어뒀고
(`b4b8264d…`, RP2350은 `5591ec52…`) 눈에 보이는 구조는 없지만 **한 샘플로는
아무것도 증명되지 않는다.** 수십 KB를 모아 오프라인 통계 검정이 필요하다.
`wiz_entropy_raw()`가 그 입구다. 대량 덤프 모드는 아직 없다.

### 6-5. ECC 상호운용성 — 조사 완료 (2026-10-15), 답은 "안 된다"

성능 질문은 전부 닫혔고, 이 항목이 제품 구조를 결정했다.

**외부 조사 결과다. 자사 실측이 아니다.** 공개 제조사 문서 기준이며
실연결 시험으로 확인한 것이 아니다.

| 클라이언트 | ECC_nistP256 | Basic256Sha256 |
|---|---|---|
| Siemens SIMATIC / WinCC | 미지원 (정책 목록에 없음) | 지원 |
| Beckhoff TwinCAT | 미지원 | 지원 |
| Ignition 8.1 / 8.3 | 미지원 (API 허용 목록 6종에 없음) | 지원 |
| PTC KEPServerEX | 미지원 | 지원 |
| Prosys OPC UA Browser 2026.2.0 | 미지원 (SDK enum에도 없음) | 지원 |
| Python asyncua | 미지원 (구현 요청 이슈 Open) | 지원 |
| UAExpert | **미확인** | 지원 |
| node-opcua | **미확인** (문서 상충) | 지원 |

**ECC만 제시하는 서버는 공통 SecurityPolicy가 없어 SecureChannel을 못 연다.**
프로토콜 수준 조건이지 UI 문제가 아니다.

표준상으로는 ECC가 필수가 아니다 — 2025 Minimum Client Facet과 Nano Embedded
Device Server Profile에서 ECC는 optional이다. **즉 Siemens·Beckhoff가 ECC를
지원하지 않는 것은 표준 위반이 아니다.** "OPC UA 1.05 지원"이 ECC 지원을
뜻하지 않는다.

### 6-6. ⚠ 우리가 측정한 정책은 deprecated다

**가장 중요한 추가 발견이다.** 벤치마크한
`http://opcfoundation.org/UA/SecurityPolicy#ECC_nistP256`은 현재 OPC Foundation
Profile DB에서 **Deprecated**이고, 후속은 **`ECC_nistP256-AesGcm`**이다
(비-AEAD → AEAD 전환). 외부 조사 결과이며 자사 확인은 아니다.

**자사 확인된 의존성:**

```
libraries/open62541   10022ffbc   2026-05-24   v1.5.4-224
ECC 정책 파일          eccnistp256 · eccnistp384 · eccbrainpoolp256r1 · eccbrainpoolp384r1
AesGcm/ChaChaPoly     0건
deprecated 표기        없음
```

**우리 트리에는 후속 정책이 아예 없다.** 조사가 인용한 "open62541 master가
non-AEAD ECC를 deprecated로 표기"는 2026-05-24 이후 변경이다.
**AesGcm으로 가려면 open62541 업그레이드가 선행된다.**

실무적 의미: **259 ms / 372 ms라는 P-256 성능 측정값은 그대로 유효하다** —
곡선 연산 비용은 정책 포장이 바뀌어도 거의 같다. 다만 **그 URI를 제품의 최종
인터페이스로 고정하면 안 된다.**
