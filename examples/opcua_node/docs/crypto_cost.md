# RSA / ECC 암호 연산 비용 — 실측

**측정일:** 2026-10-15 (RSA 4회, ECC 4회, 전부 실기)
**도구:** `examples/crypto_bench`, `tools/bench_matrix.sh`
**저장소 상태:** `273e868` + 미커밋 변경

---

## 1. 결론

**부품은 RP2350으로 간다. 그리고 정책은 ECC가 RSA보다 압도적으로 싸다.**

| | RSA-2048 (Basic256Sha256) | ECC P-256 |
|---|---|---|
| RP2040 @200MHz | 5,050 ms — **불가** | **384 ms** |
| RP2350 @150MHz | 1,229 ms — 가능 | **264 ms** |

기준은 open62541 클라이언트의 기본 타임아웃 5,000 ms다.

세 가지가 확정됐다.

1. **RP2040에서 RSA-2048은 어떤 설정으로도 안 된다.** 이미 정격(133 MHz)을
   넘긴 200 MHz에서 측정했고 그래도 타임아웃을 넘는다.
2. **ECC 정책을 쓰면 두 부품 모두 보안이 성립한다.** RP2040조차 384 ms다.
3. **동시 접속 문제가 사라진다.** 4개 동시 핸드셰이크가 RP2040 1,536 ms,
   RP2350 1,056 ms다.

**"RP2040은 보안이 불가능하다"는 2026-10-15 오전의 결론은 틀렸다.** RSA만
측정하고 내린 결론이었다. 정확한 서술은 **"RP2040에서 RSA-2048 정책은 불가,
ECC 정책은 가능"**이다.

단, RP2040 보안 등급에는 **난수 전제**가 붙는다 (6-4 참조).

## 2. 측정 환경

4개 이미지를 한 스크립트로 빌드해 교차 오염을 막았다. 이 저장소에는
`crypto_bench.uf2`를 만드는 빌드 디렉토리가 여러 개 있어서, **어느 이미지였는지가
기록되지 않으면 수치가 무의미해진다.** 그래서 이미지가 부팅 시 스스로 보고한다.

```
================ crypto_bench ================
  board    W6300_EVB_PICO2
  part     RP2350 (Cortex-M33)
  clk_sys  150000000 Hz
  bignum   assembly (MBEDTLS_HAVE_ASM)
  ecp      NIST_OPTIM on
  git      273e868
  built    2026-10-15T02:16:02Z
==============================================
```

벤치는 네트워크를 쓰지 않는다(`pico_stdlib` + `mbedcrypto` + `mbedx509`만 링크).
**이더넷 칩은 이 수치에 무관하다** — 보드 이름은 MCU와 핀 정의만 고른다.

### 배너가 실제로 사고를 잡았다

ECC 재측정 때 **빌드 완료 3초 전에 플래시가 끝나** 옛 이미지가 올라갔다.
배너에 `ecp` 줄이 없고 `built` 시각이 이전 빌드였기 때문에 즉시 발견했다.
그 줄이 없었으면 "NIST_OPTIM을 켜도 변화 없음"이라는 **거짓 결론**을 기록했을 것이다.

### 클럭이 공정하지 않다 — RP2040 쪽이 유리하게 측정됐다

`CMakeLists.txt:147`이 `PICO_USE_FASTEST_SUPPORTED_CLOCK=1`을 전역으로 건다.

```
RP2040   platform_defs.h:86    → 200 MHz   (데이터시트 정격 133 MHz, 즉 오버클럭)
RP2350   platform_defs.h:115   → 150 MHz   (정격 최대, 스톡)
```

RP2040은 정격을 1.5배 넘긴 상태이고 RP2350은 스톡이다. 그래도 RSA에서 4.1배
차이가 난다.

## 3. 실측값

### 3-1. OPC UA 보안 핸드셰이크 — RSA-2048 (ms)

| | bignum C | bignum 어셈블리 |
|---|---|---|
| RP2040 @200MHz | 6,973 | 5,050 |
| RP2350 @150MHz | 2,017 | **1,229** |

사이클 수로 환산하면 부품 효과는 5.48배다 (1,010M → 184M 사이클).
Cortex-M33에 32×32 곱셈 명령이 있고 M0+에는 없다는 차이가 그대로 나온다.

### 3-2. 같은 핸드셰이크 — ECC P-256 (ms)

| | NIST_OPTIM 꺼짐 | NIST_OPTIM 켜짐 |
|---|---|---|
| RP2040 @200MHz | 2,458 | **384** |
| RP2350 @150MHz | 1,697 | **264** |

합계 구성(어셈블리 + NIST_OPTIM):

| 연산 | RP2040 | RP2350 |
|---|---|---|
| 임시 키쌍 생성 (ECDH keygen) | 43.69 | 30.86 |
| 키 합의 (ECDH agree) | 118.18 | 78.61 |
| 서명 1회 (ECDSA sign) | 49.26 | 35.74 |
| 상대 검증 1회 (ECDSA verify) | 169.96 | 116.87 |
| 키유도 | 2.98 | 1.94 |
| **합계** | **384.07** | **264.02** |

부품 효과는 1.45배(시간), 사이클로는 1.94배다. **RSA의 5.48배와 비교하면
훨씬 작다** — ECC의 병목은 곱셈보다 모듈러 감산과 점 연산에 있고, M33의
곱셈기와 어셈블리 경로가 그만큼 덜 먹는다. 측정값에서 읽은 것이고 원인은 추정이다.

### 3-3. 개인키 연산 — RSA (ms)

| 연산 | RP2040 asm | RP2040 C | RP2350 asm | RP2350 C |
|---|---|---|---|---|
| RSA-2048 sign | 1,647 | 2,274 | **402** | 659 |
| RSA-2048 OAEP decrypt | 1,544 | 2,128 | **381** | 621 |
| 첫 sign (blinding 캐시 없음) | 1,895 | 2,566 | 551 | 825 |

### 3-4. 공개키 연산 — RSA (ms)

| 연산 | RP2040 asm | RP2040 C | RP2350 asm | RP2350 C |
|---|---|---|---|---|
| RSA-2048 verify | 103.5 | 146.5 | **21.1** | 38.1 |
| RSA-2048 OAEP encrypt | 104.0 | 147.0 | **21.4** | 38.3 |

### 3-5. 메시지마다 드는 비용 — SignAndEncrypt, 8 KB

Basic256Sha256은 메시지를 암호화하면서 **서명도 한다.** 둘 다 들어간다.

| | RP2040 | RP2350 |
|---|---|---|
| AES-256-CBC 8 KB | 6.32 ms | 4.00 ms |
| HMAC-SHA256 8 KB | 5.08 ms | 2.75 ms |
| **합계** | **11.40 ms → 5.75 Mbit/s** | **6.75 ms → 9.71 Mbit/s** |
| (AES만 보면) | 10.37 Mbit/s | 16.38 Mbit/s |

**AES 행만 인용하면 약 2배 과장이 된다.** 괄호의 수치를 보안 처리량으로
쓰면 안 된다. 벤치 출력 자체에 그 경고를 넣어 뒀다.

참고 — SHA-256 8 KB는 RP2040 4.96 ms / RP2350 2.65 ms다. HMAC의 고정
오버헤드는 0.12 ms뿐이다.

### 3-6. 파싱

| 연산 | RP2040 | RP2350 |
|---|---|---|
| 개인키 DER 파싱 | 약 215 us | 약 190 us |
| 인증서 파싱 | 약 160 us | 약 157 us |

시작 시 1회 / 클라이언트당 1회라 무게가 없다.

## 4. 설정 하나가 ECC를 6.4배 바꿨다 — 가장 중요한 발견

```
MBEDTLS_ECP_NIST_OPTIM     P-256 전용 빠른 모듈러 감산
```

이 옵션이 우리 설정에 **없었다.** 켜고 재측정한 결과:

```
RP2040   2,458 → 384 ms    6.40배
RP2350   1,697 → 264 ms    6.43배
RSA      변화 없음          (소수점까지 동일 — 옵션이 ECC만 건드렸다는 확인)
```

비용은 **코드 증가, RAM 증가 없음.** `.text`가 RP2040 122,276 → 129,676,
RP2350 114,128 → 121,368이다. 단 이 증가분에는 **ECC 벤치 코드와 최적화가
같이 들어 있어** 둘을 분리한 값은 측정하지 않았다.

### 왜 빠져 있었나 — 재발 방지가 필요한 구조

우리 빌드는 `MBEDTLS_CONFIG_FILE`로 `port/mbedtls/inc/ssl_config.h`를 쓴다.
**이 파일은 상위 `mbedtls_config.h`를 보강하는 것이 아니라 완전히 교체한다.**
따라서 mbedTLS 기본값으로 켜져 있던 옵션(`mbedtls_config.h:784`)이 조용히 꺼졌다.

**같은 이유로 꺼져 있는 다른 옵션이 더 있을 수 있다. 미확인이다.**
성능이 예상보다 나쁘면 알고리즘을 의심하기 전에 이 파일을 먼저 볼 것.

### 이 발견 전에 두 번 틀린 판단을 했다

1. "ECC는 수십 ms일 것" — 실측 2,458 ms. 5배 이상 틀렸다
2. "RP2350에서 ECC가 RSA보다 비싸니 ECC 경로를 닫자" — 실측 264 ms로 4.7배 싸다

둘 다 **설정이 틀린 상태의 측정값으로 알고리즘을 판단**한 결과다.

## 5. 이 숫자가 아닌 것

**바닥값이다.** 산술만 재고 왕복·인코딩·PKI 목록 순회·DRBG 시딩·할당·이더넷
전송이 빠져 있다. 실제 클라이언트가 보는 시간은 더 길다.

**인증서 체인 검증값은 유효하지 않다.** `crypto_bench.c`가 같은 인증서를
leaf와 trust anchor로 둘 다 넣어서 mbedTLS가 즉시 통과시킨다(25~44 us).
진짜 검증은 공개키 연산 1회라 RSA에서 RP2350 약 21 ms다. **미수정.**

**RP2350에서 설명되지 않은 값.** HMAC 32 B와 키유도가 어셈블리 설정에 따라
움직였다(106.2 → 135.0 us). SHA 8 KB와 AES 8 KB는 소수점까지 같고 RP2040에서는
HMAC도 같았다. 코드 배치 변화로 XIP 캐시(8 KB) 적중률이 달라진 것이 후보지만
**확인하지 않았다.** 설계 판정에는 영향이 없다.

## 6. 설계 판정

### 6-1. 워치독은 존재하지 않는다

`crypto_bench`와 `current_state.md:170`이 "RSA 연산 중 워치독이 kick되지
않는다"고 서술하지만, **`examples/opcua_node`에는 워치독이 없다.**
`watchdog_enable()` 호출이 없고 `opcua_settings.h:149`의 `reboot_reason`에
`1=watchdog` 값만 정의돼 있다.

현재 결함이 아니다. 넣을 때 타임아웃을 핸드셰이크 시간보다 충분히 길게 잡는다.

### 6-2. 동시 핸드셰이크 — ECC를 쓰면 해소된다

이벤트루프가 한 번의 iterate에서 소켓 4개를 순서대로 돈다
(`open62541_wiznet_eventloop.c:827,833`). 단일코어 협력 루프라 OPN 처리는 직렬이다.

```
RSA   RP2350   4 × 1,229 = 4,916 ms    ← 타임아웃 경계
ECC   RP2350   4 ×   264 = 1,056 ms    ← 여유 큼
ECC   RP2040   4 ×   384 = 1,536 ms    ← 여유 큼
```

**소켓 수를 2개로 줄이는 안은 폐기할 수 있다** — ECC 정책을 쓰는 한.
RSA로 가면 다시 살아난다.

### 6-3. RSA 연산은 쪼갤 수 없고 ECC는 쪼갤 수 있다

벤더링된 mbedTLS 3.6.0에 `MBEDTLS_ECP_RESTARTABLE`은 있으나
(`mbedtls_config.h:839`) **RSA에 대응되는 기능이 없다**(`rsa_restart` 심볼 부재).

즉 ECC 정책에서는 핸드셰이크를 여러 루프 이터레이션에 나눠 양보시킬 수 있다.
264 ms라면 굳이 필요 없을 수도 있다 — 필요해지면 그때 켠다. 현재 꺼져 있다.

### 6-4. 엔트로피 — RP2040 보안 등급의 전제

**RP2350에 하드웨어 TRNG가 있다. SDK 코드로 확인됐다.**

```
rp2350/hardware_regs/include/hardware/platform_defs.h:74    HAS_RP2350_TRNG 1
rp2_common/pico_rand/include/pico/rand.h:76,102              기본 엔트로피원으로 TRNG 사용
rp2350/hardware_structs/include/hardware/structs/trng.h      존재
```

**RP2040에는 없다.** 그리고 **ECDSA는 서명마다 난수를 쓴다** — 그 난수가
예측 가능하거나 재사용되면 개인키가 노출된다. 성능이 아니라 보안 문제다.

```
RP2350   ECC 264 ms · RSA 1,229 ms · TRNG 있음     → 보안 등급 성립
RP2040   ECC 384 ms · RSA 불가     · TRNG 없음     → 난수 해결이 전제
```

**RP2040 보안 등급은 성능으로 열렸고 난수로 막혀 있다.** ROSC 기반 난수의
품질 근거를 문서화하거나 외부 난수 칩이 필요하다.

**양쪽 모두 아직 연결 안 돼 있다.** `mbedtls_hardware_poll`도
`MBEDTLS_ENTROPY_HARDWARE_ALT`도 저장소에 없다. 암호화를 켜기 전에 해야 한다.

### 6-5. 남은 유일한 성능 외 게이트 — ECC 상호운용성

성능 질문은 전부 닫혔다. 남은 것은 **현장 클라이언트가 ECC 정책
(`ECC_nistP256`)을 제시하는가**다.

`libraries/open62541/plugins/crypto/mbedtls/`에 ECC 정책 플러그인 4개가 이미 있다
(`securitypolicy_eccnistp256.c` 등). 서버 쪽 구현은 문제가 아니다.

**이건 측정이 아니라 조사다.** UAExpert와 주요 PLC/SCADA 클라이언트가 어떤
정책을 지원하는지 확인해야 한다. 안 되면 RSA로 돌아가고, 그러면 RP2040은
평문 등급이고 RP2350도 1,229 ms를 안고 간다.

## 8. 재현 절차

```bash
cd /d/theo_git_project/WIZnet-PICO-C-CHIP-TEST
bash tools/bench_matrix.sh                       # 4개 이미지 빌드
bash tools/bench_matrix.sh --flash rp2350_asm    # BOOTSEL 보드로 복사
# 실행 중인 보드를 호스트에서 BOOTSEL로 넣기 (터미널을 먼저 닫아야 한다):
bash tools/bench_matrix.sh --flash rp2350_asm COM12
```

`build_bench_out/manifest.txt`에 variant · 보드 · bignum · md5 · 시각이 남는다.

**시리얼 출력의 배너가 의도한 부품·설정과 다르면 그 로그는 버린다.**
`bignum`과 `ecp` 두 줄을 반드시 확인한다 — 빌드와 플래시가 겹치면 옛 이미지가
올라간다(2장 참조).

A/B 스위치:

```
-DBENCH_NO_ASM=1          bignum 어셈블리 끄기
-DBENCH_NO_ECP_OPTIM=1    NIST 곡선 최적화 끄기
```

보드 두 개가 필요하다: `W55RP20_EVB_PICO`(RP2040), `W6300_EVB_PICO2`(RP2350).
